# Промт для Claude Code — версия 1 (локально)

Как запускать: открой терминал в папке `bani-pwa`, запусти `claude`, вставь **Промт старта**. Когда этап закончится и агент остановится — новая сессия (`/clear`) и **Промт продолжения**. Так контекст не переполняется, а прогресс живёт в `PROGRESS.md` и git.

---

## Промт старта

Ты реализуешь PWA онлайн-бронирования для бань и саун с почасовой арендой залов по docs/IMPLEMENTATION-PLAN.md. Прочитай весь документ, AGENTS.md и CLAUDE.md до начала работы.

Цель — законченный работающий продукт, который можно переодеть под следующее заведение через один business.json и изображения, сохранив работу всех ранее опубликованных заведений.

**Версия 1 работает полностью локально.** Supabase — только локальный стек в Docker (`supabase start`, `supabase functions serve`, `supabase test db`). Не создавай облачный проект, не делай `supabase link`, не деплой. LLM-ключа нет: AI-модуль реализуй полностью, в тестах используй скриптованный провайдер с явной пометкой «тестовый», в UI без ключа — состояние «AI недоступен». Это не моки интеграции: всё, кроме внешних сервисов, должно реально работать против локального стека.

Создай приложение, миграции Supabase, Edge Functions, скрипты конвейера и документацию. Не останавливайся на макете интерфейса. Не называй моковые ответы интеграцией. Не генерируй проект одним гигантским файлом.

Порядок работы:
- Сначала проверь существующие файлы (там уже стоят скилы в .claude/skills, AGENTS.md, CLAUDE.md, package.json-заготовка) и сохрани их.
- Реализуй этапы 1–8 последовательно. После каждого этапа запусти его проверки из плана, запиши результат в PROGRESS.md, сделай git commit.
- **В этой сессии выполни этапы 1 и 2, затем остановись** и выведи краткий отчёт: что сделано, какие проверки зелёные, что следующее.
- Не проси уточнять технические решения, уже определённые в плане. Если чего-то нет на машине (Docker не запущен, нет Supabase CLI) — остановись и скажи точную команду установки.

Стек: React 19, TypeScript strict, Vite, React Router, TanStack Query, Zod, Astryx (основная UI-библиотека) + shadcn/ui только для отсутствующих в Astryx компонентов, Supabase Postgres/Auth/Storage/Edge Functions, vite-plugin-pwa injectManifest. Frontend статический, готовый к Cloudflare Pages. Отдельный Node backend не нужен.

Astryx: установи и инициализируй командами из плана (раздел «Команды Astryx»). Прочитай блок, который `astryx init` допишет в CLAUDE.md, и документацию реально установленной версии (`npx astryx docs ...`). Запускай `npx astryx component <Name>` перед использованием любого компонента с незнакомыми props. Используй поставляемый Astryx CSS и документированный `Theme`. Bottom sheet — только Astryx `BottomSheet`, второй реализации Drawer не добавляй. Если подключаешь shadcn — проверь единые токены и порядок CSS layers по `npx astryx docs styling-libraries tailwind`. Зафиксируй зависимости в lockfile.

Дизайн: перед экранами используй скил ui-ux-pro-max для дизайн-системы (тёмная, спокойная, плотная, wellness/банная тематика, тёплый акцент), сохрани её в design-system/. Тёмное мобильное приложение, один акцент из конфигурации заведения, выразительные фото залов, короткий путь брони (зал → дата → время и длительность → гости и допы → контакты), нижняя навигация, последовательная bottom sheet. Учти safe area, клавиатуру, Back, focus management, reduced motion. UI на русском, рубли, timezone заведения. Кабинет удобен на телефоне: владелец вносит бронь, принятую по телефону или в мессенджере, за пару нажатий — приложение его единственный календарь. У каждой кнопки реальное действие, у каждого сетевого экрана состояния loading/error/empty/success. В форме гостя — согласие на обработку персональных данных со ссылкой на политику заведения.

Архитектурные инварианты:
1. Один общий JS/CSS-билд, один Supabase-проект, tenant_id во всех зависимых данных; /s/{slug}/ и /s/{slug}/owner/. Новое заведение не заменяет предыдущее.
2. business.json и изображения — вход конвейера; БД — runtime-источник. Скрипты tenant:new, tenant:validate, tenant:publish, tenant:verify реально работают против локального стека и описаны в package.json.
3. Бронь занимает конкретный зал на непрерывный диапазон: минимальная длительность в часах, шаг слота, буфер на уборку и протопку между гостями, переход через полночь и круглосуточная работа. Рабочие часы задают моменты начала брони. Цена считается на сервере по тарифу дня и времени (будни/выходные/ночь), числу гостей сверх включённого в зал и выбранным допам. Проверяй исключения, timezone и границы дат.
4. Бронирование и блокировка зала используют одну resource_occupancies с PostgreSQL EXCLUDE. Создание/перенос/отмена — атомарные SQL-транзакции. Клиент не задаёт цену, tenant и время окончания. Повторные запросы идемпотентны; неудачный перенос не теряет исходную бронь.
5. Гость бронирует без регистрации. Доступ к одной брони по криптографическому токену, в БД только hash; повторная выдача того же токена при retry (HMAC от booking_id и idempotency key, см. план). Владелец входит через Supabase Auth, его tenant подтверждается членством на сервере. Публичного owner signup нет.
6. RLS, составные tenant FK и строгие GRANT; anon не видит персональные данные, платежи и токены. Service-role и LLM API key только на сервере. Приватный кэш очищается при logout и не попадает в service worker.
7. AI через настраиваемые LLM_BASE_URL/LLM_API_KEY/LLM_MODEL. До ответа про брони сервер выполняет разрешённый инструмент и передаёт результат модели. SQL и tenant_id модель не выбирает. Гостевые и owner tools разделены проверкой полномочий. Ограниченный tool loop и JSON-intent fallback, роутер тестируется отдельно.
8. Статистику считает SQL. Разделяй брони, состоявшиеся визиты и полученные платежи (включая задатки); будущая стоимость — «ожидается», не выручка. Период и timezone одинаковы в UI и AI.
9. У каждого tenant свои HTML-метаданные, manifest id/start_url/scope, icon, maskable icon, apple-touch-icon, startup assets. Общие исходники, отдельные worker scopes и имена кэшей. Глубокие ссылки отдают оболочку правильного заведения (проверка через `wrangler pages dev`).
10. Web Push через VAPID (ключи сгенерировать локально), pg_cron и outbox notification_jobs с lease, дедупликацией и обработкой переноса/отмены. ICS — дополнительный канал с честным состоянием в интерфейсе. Не обещай push обычной вкладке iPhone без установки.
11. Preview содержит только помеченные demo-данные и не шлёт реальные уведомления (status simulated). Live активируется после проверки бизнес-настроек. Переиздание конфига сохраняет брони, платежи и фотографии владельца.
12. Публичные запросы и бюджет LLM ограничены общими атомарными счётчиками в БД. При недоступном AI обычная бронь работает.
13. Платежи v1 — ручной ввод владельцем (задаток/оплата/возврат, способ). Модель готова к онлайн-провайдеру позже, но его интеграцию не делай.

Демо: два заведения из плана (demo-banya — 2 зала, demo-sauna24 — круглосуточная с бассейном). Демо-данные в seed, бизнес-названия не появляются в src.

Тесты (не ограничивайся скриншотом или успешным build): конкурентная бронь, два зала, бронь через полночь и минимальная длительность, буфер между гостями, блокировка зала, перенос (успех и откат), идемпотентность, RLS/tenant isolation, историческая цена, тариф по времени и доплата за гостей, платежи и задатки, DST, AI scopes и роутер, outbox. Один Playwright flow: выбор зала → подтверждение → бронь видна у владельца.

Финальные результаты (к концу этапа 8): рабочее приложение; SQL migrations и seed; Edge Functions; конвейер; .env.example без секретов; SETUP.md (локальный запуск, переменные, cron, публикация, раздел «Перенос на сервер» из плана); CLONE-IN-6-MINUTES.md; ACCEPTANCE.md с фактически выполненными проверками и списком того, что требует внешних сервисов (облачный Supabase/VPS, LLM-ключ, реальные устройства, хостинг).
